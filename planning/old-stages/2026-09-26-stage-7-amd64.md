# Stage 7: A 64-bit Windows program returns 42

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An original amd64 Windows program returns 42. Unity's player and the amd64 `Game.exe` builds need this CPU path before they need Direct3D 11.

**Architecture:** The same native ARM64 Wine process loads FEX's amd64 CPU DLL, `libarm64ecfex.dll`, built from `FEX-2609`. On ARM64, Wine runs x86-64 PE code through ARM64EC, not WoW64. Wine is configured with the `arm64ec` arch, and the CPU DLL is registered as the x86-64 emulator. Autorun does the same with a Box64 DLL it calls `winebox64ec`. Stage 4's i386 path, with `libwow64fex.dll`, stays in place.

This stage uses the Wine Unix-side build, `wineserver`, and `eikon-wine` from stage 4 Task 3. It does not need stage 4's i386 device run. An amd64 guest does not need the low 4 GB. If stage 2 closed the i386 gate, this stage is where the device path continues.

**Tech Stack:** Wine `--enable-archs=arm64ec,aarch64,i386` (the same pin as stage 4), llvm-mingw with the `arm64ec-w64-mingw32` target, FEX `libarm64ecfex.dll`, mingw-w64 `x86_64`.

## Global Constraints

- Linux guests stay on FEX. This stage is Windows amd64 only.
- The guest is `demos/windows/amd64`.
- No Direct3D in this stage. Stage 8 owns the first Direct3D 11 frame.
- No JIT bypass. Stage 3's `add42=42` is required for a device claim.
- ARM64EC is Windows ARM64 code too, so stage 2's three `helper.x18_*` lines must be `kept` for a device claim. The low-4 GB result does not matter here.
- No program titles.

### Task 1: The guest

**Files:**
- Create: `demos/windows/amd64/main.c`
- Test: `tests/test_amd64_guest.py`

**Interfaces:**
- Consumes: nothing
- Produces: `amd64.exe` whose `main` returns 42

- [ ] **Step 1: Write the program**

```c
int main(void) {
    return 42;
}
```

Build: `x86_64-w64-mingw32-gcc -O2 -o amd64.exe main.c`

Confirm with `objdump -f` that the machine is `x86-64`. Desktop Wine exits 42.

`tests/test_amd64_guest.py`:

```python
from pathlib import Path

ROOT = Path(__file__).resolve().parents[1]

def test_returns_42():
    text = (ROOT / "demos" / "windows" / "amd64" / "main.c").read_text(encoding="utf-8")
    assert "return 42;" in text
```

### Task 2: Load it

**Files:**
- Create: `docs/build-wine-amd64.md`
- Create: `plans/amd64-gap.md` only if Wine's ARM64EC side cannot load the DLL

**Interfaces:**
- Consumes: stage 4 Task 3's Wine Unix side, `wineserver`, and `eikon-wine`, used for process exit
- Produces: probe log `amd64=42`

- [ ] **Step 1: Build `libarm64ecfex.dll`**

Build from the same patched FEX tree as stage 4, with the ARM64EC triple:

```bash
cmake -S build/fex-patched -B build/fex-arm64ec -G Ninja \
    -DCMAKE_TOOLCHAIN_FILE=Data/CMake/toolchain_mingw.cmake \
    -DMINGW_TRIPLE=arm64ec-w64-mingw32 \
    -DENABLE_LTO=False -DENABLE_JEMALLOC_GLIBC_ALLOC=False \
    -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build/fex-arm64ec --target arm64ecfex
```

Check the target name against the tag. Record the commands and the DLL path in `docs/build-wine-amd64.md`.

- [ ] **Step 2: Build Wine's ARM64EC PE side and register the DLL**

Rebuild stage 4's PE half with `--enable-archs=arm64ec,aarch64,i386`. Install the DLL in `system32`. Create the registry key `HKLM\Software\Microsoft\Wow64\amd64` with its default value set to `libarm64ecfex.dll`, which is how FEX's Wine instructions select it. Record the configure line and the key in `docs/build-wine-amd64.md`.

ARM64EC needs more from Wine than WoW64 does. If upstream fails where bylaws' `upstream-arm64ec` branch works, use the pin stage 4 recorded. If stage 4 still uses upstream, record the failure in `plans/amd64-gap.md` and stop; the owner decides whether to switch the pin.
